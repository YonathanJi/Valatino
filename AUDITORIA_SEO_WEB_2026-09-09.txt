



AUDITORÍA SEO — VALATINO
Fecha: 9 de septiembre de 2026
Alcance: revisión pasiva del sitio publicado https://valatino.es y del código web.
No se ha modificado código, configuración ni contenido de la aplicación.

RESUMEN EJECUTIVO

La base SEO actual es buena y está claramente por encima de la de una tienda web
recién publicada. La web entrega contenido indexable, define una versión canónica
del dominio, cuenta con robots.txt y sitemap válidos, y las fichas de producto ya
incluyen datos estructurados útiles (precio, moneda y disponibilidad).

Las oportunidades de mejora no son una emergencia técnica. La prioridad es:

  1. Garantizar que las pantallas privadas o de utilidad no aparezcan en Google.
  2. Completar los datos de comercio/producto para resultados de compras.
  3. Crear rutas de categoría y contenido orientado a búsquedas reales.
  4. Medir indexación, rendimiento y consultas desde Search Console.

RESULTADO DE LA REVISIÓN ACTUAL

Correcto / ya implementado

- Un único dominio principal: HTTP y www redirigen con 308 a
  https://valatino.es/. Esto evita duplicidad de URL.
- Portada con title, meta description, canonical, H1 visible y HTML en español.
  Title publicado: "Catálogo — Productos Latinoamericanos | Valatino".
  H1 publicado: "Sabores de Latinoamérica".
- Las tarjetas y fichas de producto están presentes en el HTML que se entrega;
  el catálogo no depende únicamente de que el navegador del usuario ejecute
  JavaScript. Esto es positivo para Google.
- Cada ficha revisada tiene URL canónica propia, title y descripción propios,
  imagen con texto alternativo, Open Graph/Twitter y JSON-LD Product.
- El JSON-LD actual declara nombre, imagen, URL, categoría, precio numérico,
  EUR, IVA incluido, disponibilidad y vendedor. También hay BreadcrumbList.
- Existe JSON-LD de OnlineStore/WebSite, con el perfil de Instagram y España
  como zona de servicio.
- robots.txt se publica, permite la parte pública y anuncia el sitemap.
- sitemap.xml se publica correctamente con 34 URLs: la portada, 4 páginas
  informativas y 29 fichas de producto. Las rutas privadas no se anuncian.
- El código pagina el catálogo al formar el sitemap y reintenta la consulta;
  esto evita que un catálogo grande quede cortado por un límite de API.
- El catálogo utiliza imágenes optimizadas de Next con tamaños responsivos y
  texto alternativo descriptivo en las tarjetas revisadas.

HALLAZGOS Y ACCIONES RECOMENDADAS

P1 — Indexación fiable de pantallas de utilidad y acceso

Estado observado:
  /carrito, /favoritos, /login, /registro, /checkout, /cuenta, /backoffice y
  /auth están bloqueadas en robots.txt y excluidas del sitemap. Esto reduce el
  rastreo innecesario y es una buena primera capa.

Riesgo:
  robots.txt no es una orden de "no indexar". Una URL bloqueada aún puede
  aparecer en Google si otro sitio la enlaza, normalmente como un resultado sin
  descripción. Además, estas rutas se enlazan internamente desde la cabecera.

Acción para desarrollo:
  - Añadir meta robots/X-Robots-Tag "noindex, follow" a las pantallas públicas
    de utilidad que sí se pueden cargar sin iniciar sesión: carrito, favoritos,
    login, registro y checkout.
  - Para que Google pueda leer ese noindex, evaluar retirar del Disallow solo
    esas pantallas públicas una vez que el noindex esté desplegado. Mantener
    protegidas por autenticación las zonas privadas y el panel administrativo.
  - Conservar /api/ y callbacks de autenticación fuera del rastreo; no deben
    formar parte del índice.
  - Validar las cabeceras y el HTML final con Inspección de URL de Search Console.

Criterio de aceptación:
  Ninguna URL de carrito, cuenta, acceso, checkout ni administración aparece
  como página indexada en Search Console. El acceso al panel sigue exigiendo
  autenticación y rol; SEO no sustituye esos controles de seguridad.

P1 — Hacer veraz la fecha de actualización del sitemap

Estado observado:
  Las cinco URLs fijas del sitemap se emiten con la fecha y hora de cada
  regeneración. Al revisarlo, todas figuraban modificadas el 09/09/2026, aunque
  sus frecuencias declaradas son anual o diaria.

Impacto:
  El campo lastmod debería cambiar únicamente cuando cambió de forma relevante
  la página. Actualizarlo cada pocos minutos no aporta señal útil y puede reducir
  la confianza en esa indicación.

Acción para desarrollo:
  - Para portada y legales, usar la fecha real de publicación/última edición.
  - Para producto, conservar updated_at, que ya es la decisión correcta.
  - No usar la hora de generación como lastmod.
  - Eliminar changefreq y priority si se desea simplificar: Google no los usa
    como instrucciones de frecuencia o prioridad.

Criterio de aceptación:
  Dos descargas consecutivas del sitemap sin cambios de contenido devuelven el
  mismo lastmod para las URLs fijas.

P1 — Datos estructurados orientados a Merchant Listings

Estado observado:
  Las fichas ya tienen Product + Offer y, por ello, un buen punto de partida para
  precio y disponibilidad en Google. Las variantes tienen URL individual, lo
  cual también es correcto.

Acción para desarrollo y catálogo:
  - Ampliar el modelo de producto para conservar, cuando el fabricante los
    proporcione: marca, SKU, GTIN/EAN o MPN y condición (NewCondition).
  - Emitir esos campos en JSON-LD solo cuando sean datos reales y verificables.
    Nunca inventar un GTIN ni reutilizarlo entre presentaciones distintas.
  - Añadir política de devolución común al Organization/OnlineStore y detalles
    de envío al Offer cuando importe, regiones y condiciones estén definidos de
    manera exacta. Las condiciones actuales hablan de 14 días y devoluciones;
    el marcado debe reproducir exactamente la política legal, no una versión
    aproximada.
  - Cuando haya catálogo suficiente y operación estable, activar las fichas
    gratuitas en Google Merchant Center y mantener feed, página y stock
    sincronizados.

Criterio de aceptación:
  Rich Results Test y el informe Merchant listings de Search Console no muestran
  errores. Precio, disponibilidad y política declarados coinciden con la página,
  checkout y catálogo.

P2 — Categorías indexables e intención de búsqueda

Estado observado:
  La portada es el único listado de catálogo. Las categorías (por ejemplo,
  Bebidas, Dulces, Galletas o Despensa) aparecen como texto en las tarjetas,
  pero no tienen páginas ni enlaces de categoría propios.

Impacto:
  La web depende casi por completo de búsquedas de marca o de producto exacto.
  Pierde oportunidades para búsquedas como "dulces colombianos en España",
  "bebidas colombianas online", "galletas colombianas" o "productos
  latinoamericanos en [ciudad]" (solo si realmente se envía allí).

Acción para desarrollo y contenido:
  - Crear URLs permanentes y navegables por categoría, por ejemplo
    /categorias/dulces, /categorias/bebidas y /categorias/galletas.
  - Añadir enlaces HTML visibles desde portada, menú o bloque de categorías;
    incluir las nuevas páginas en sitemap con canonical propio.
  - En cada categoría: H1 específico, breve introducción útil, listado de
    productos y enlaces a sus fichas. Evitar párrafos genéricos repetidos.
  - Decidir una lista de consultas objetivo con datos de Search Console y
    Keyword Planner antes de redactar grandes volúmenes de contenido.

Criterio de aceptación:
  Cada categoría tiene una URL 200, title/H1/description únicos, enlaza a sus
  productos y se puede descubrir desde la portada sin buscarla manualmente.

P2 — Consolidar variantes y nombres visibles

Estado observado:
  En fichas de variantes el title usa el nombre completo del producto, pero el
  H1 puede mostrar solo el nombre de la familia y dejar la presentación en un
  texto secundario. Ejemplo de patrón: H1 "Nucita" y presentación "Caja 12
  unidades".

Acción para desarrollo:
  - Mostrar en el H1 el nombre comercial completo de la URL actual, por ejemplo
    "Nucita — Caja de 12 unidades". Mantener el selector de presentaciones como
    navegación interna hacia las demás URL de la misma familia.
  - Revisar que cada variante tenga descripción, foto, precio y disponibilidad
    propios si seguirá teniendo URL indexable.
  - Si alguna presentación no tiene contenido diferenciable o no se venderá de
    forma independiente, decidir si debe redirigirse, canonicalizarse o dejarse
    fuera del sitemap. No aplicar canonical masivos sin una revisión producto a
    producto.

Criterio de aceptación:
  H1, title, JSON-LD, imagen y precio describen la misma presentación concreta.

P2 — Calidad de imágenes y ficha de producto

Estado observado:
  La mayoría de las fichas tienen imágenes propias optimizadas. Se detectó al
  menos una presentación activa que usa /placeholder.png (Bon Bon Bum unidad).

Impacto:
  Una imagen genérica reduce la calidad de la ficha, la tarjeta social y la
  elegibilidad visual del producto.

Acción para catálogo:
  - Sustituir la imagen provisional por una foto propia y representativa antes
    de promocionar o reponer esa presentación.
  - Establecer una validación editorial: producto activo e indexable requiere
    nombre, descripción útil, imagen propia, precio, categoría y disponibilidad.
  - Mantener texto alternativo breve que identifique el producto y presentación;
    no llenar el atributo alt con palabras clave repetidas.

P3 — Identidad de marca y presentación en buscadores

Acción recomendada:
  - Añadir icono/favicon y manifest si aún no existe un activo de marca propio.
    La revisión de código no encontró archivos de manifest, icon o favicon.
  - Sustituir la imagen genérica de portada usada como logo estructurado por un
    logo oficial cuando esté disponible. No declarar como logo una imagen que
    no represente de manera estable a la marca.
  - Mantener Instagram enlazado desde su biografía a la web; sameAs ayuda a
    relacionar identidades, pero no crea por sí solo enlaces entrantes.

MEDICIÓN Y OPERACIÓN SEO (IMPRESCINDIBLE)

No es posible concluir desde una revisión pública si Google ya ha indexado cada
URL, por qué términos aparece o cuáles son sus Core Web Vitals de usuarios reales.
Configurar y revisar estas herramientas es el siguiente paso:

1. Google Search Console
   - Verificar la propiedad de dominio valatino.es.
   - Enviar https://valatino.es/sitemap.xml.
   - Revisar semanalmente: Páginas indexadas, Sitemaps, Merchant listings,
     Core Web Vitals, Acciones manuales y Problemas de seguridad.
   - Inspeccionar portada, tres productos con stock, un producto sin stock,
     una categoría futura y las rutas noindex.

2. Google Merchant Center (cuando los datos comerciales estén completos)
   - Activar listados gratuitos.
   - Comparar regularmente precio y disponibilidad detectados con la tienda.

3. Rendimiento
   - Ejecutar PageSpeed Insights en móvil y escritorio de la portada y varias
     fichas. Corregir primero LCP, INP y CLS confirmados por medición, no por
     intuición.
   - Vigilar que la API de catálogo no provoque HTML incompleto o respuestas
     lentas durante arranques en frío; el sitemap ya tiene reintentos, pero
     portada y fichas también necesitan una experiencia estable para robots y
     visitantes.

PLAN DE IMPLEMENTACIÓN PROPUESTO

Semana 1
  - Acordar estrategia noindex/robots de rutas de utilidad.
  - Corregir lastmod de rutas fijas del sitemap.
  - Abrir Search Console y enviar sitemap.

Semanas 2–3
  - Incorporar marca/SKU/GTIN cuando existan y marcado de devoluciones/envíos
    validado contra la política comercial.
  - Revisar H1 de variantes y sustituir imágenes provisionales.
  - Validar con Rich Results Test y desplegar sin advertencias nuevas.

Mes 1–2
  - Lanzar categorías indexables con contenido útil y enlaces internos.
  - Activar Merchant Center/listados gratuitos si la operativa y datos están
    completos.
  - Priorizar mejoras de rendimiento a partir de datos de PageSpeed y Search
    Console.

NOTA FINAL

El SEO técnico no es una garantía de posiciones. Valatino ya tiene una base limpia
para que Google descubra y entienda la tienda; el crecimiento dependerá después de
contenido útil por categoría, catálogo bien documentado, experiencia rápida,
disponibilidad real y señales externas de confianza.
